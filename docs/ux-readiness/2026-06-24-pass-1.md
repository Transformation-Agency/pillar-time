# UX Readiness Audit - Pass 1

Date: 2026-06-24
Scope: installed `v0.2.3` app plus local development build.

## Methods

- Launched `/Applications/Pillar Time.app` and verified the backend sidecar stayed running on port `42818`.
- Inspected the live Today page through the accessibility tree.
- Started a disposable development server on `http://127.0.0.1:43996/#today`.
- Inspected first-run/empty Today, onboarding code paths, approval execution paths, and Calendar recovery state.
- Ran `npm test` and `npm run build`.

## Findings

### P1 - Calendar approval recovery became a dead-end

The latest completed day plan showed proposed calendar blocks, but the matching calendar approval had status `approved` and a failed execution note: `Reconnect Google Calendar to allow approved schedule writes.` Today only looked for `pending` approvals, so it rendered a disabled `Approve Calendar` button with no recovery explanation.

Impact: a real user sees the proposed schedule, believes there should be one obvious action, and cannot tell whether the calendar was already written, failed, or needs reconnect.

Fix implemented:
- Today now matches the proposal approval for the artifact regardless of status.
- Pending proposals show `Approve Calendar`.
- Approved-but-not-executed proposals show `Retry Calendar Write`.
- Executed and rejected proposals render as terminal states.
- Failed Calendar write-scope approvals show an inline recovery note and an `Open Settings` button.
- Added a guardrail test for the approved-but-not-written recovery copy.

### P2 - First-run Today is understandable but slightly passive

The empty Today state is serviceable: it shows one starter suggestion, a quick-capture input, context intake, and empty agenda copy. It does not force onboarding after manual skip, which is acceptable, but the page relies on the user to infer that `Generate Day Plan` is safe without Calendar or Linear connected.

Recommended next fix:
- Add a small preflight line under `Generate Day Plan` when Calendar, Linear, or model are missing: "Runs locally with available context; missing connectors will be reported."

### P2 - External write tests must avoid real credentials

The disposable dev server still surfaced real Google Calendar credential state, so this pass did not execute Calendar writes. The UI code path was verified by source inspection and tests, not by live mutation.

Recommended tests:
- Add a fixture-level UI test for `calendar.proposed_schedule` statuses: pending, approved with reconnect note, executed, rejected.
- Add an API test that Calendar execution failure preserves a retryable user state and exposes a clear resolution note.
- Add a first-run smoke test that asserts empty Today has capture, context intake, and connector-independent generate affordances.
