## Methods

- Verified the first pass fix merged to `main` through PR #21 before starting this branch.
- Ran `npm test` and `npm run build`.

## Findings

### P1 - Calendar Settings hid read/write permission mismatch

Google Calendar could be `status: ready` while `canWrite: false` and `writeStatus: needs reconnect`. Settings still labeled it as simply `Connected`, which made it hard to understand why approved schedule blocks failed to write.

Impact: a user can believe Google Calendar is fully connected, approve a proposed calendar, and then get a failure that appears contradictory.

Fix implemented:
- Settings research table now distinguishes:
  - `Read/write ready`
  - `Read ready · reconnect to write`
  - `Needs consent`
  - `Needs OAuth`
- Google Calendar modal now explains that reads power planning, writes only happen after approval, and older read-only tokens need reconnect.
- Primary button changes to `Reconnect for Calendar Writes` when the current token lacks write scope.
- Added guardrail strings to the runtime separation test.

## Remaining Friction

- The Google OAuth callback page is functional, but still plain. Later pass should confirm copy in Chrome when consent succeeds/fails.
- Linear missing-key state is better than before, but it could offer a direct "Where do I find this?" link inside the modal.
- Telegram delivery now has soft timeout handling in backend, but the Brief list still only shows `Delivered` or `Saved`; it should eventually distinguish `ack pending`.
